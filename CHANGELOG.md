### Score Distribution radar: never clips, and an exploded full-size view
- **What you asked for.** "Score distribution image needs to be able to show an exploded view or be centered."
- **Root cause.** The radar's canvas had a fixed size (`viewBox="0 0 220 190"`); a section name long enough, or a set with enough sections, ran past the edge of that box on whichever side had the longest label, and SVG silently clips anything drawn outside its own viewBox — so the chart looked lopsided or cut off depending on how many sections an assessment scored and how long their names were.
- **Fix.** The viewBox is now computed from the actual label set every time it draws, sized just wide and tall enough to hold the longest label on every side — so the circle is always centred and nothing is ever clipped, regardless of how many sections there are or how long their names run (real assessments commonly score 12 sections). A new expand button (⤢) on the Score Distribution tile opens a full-size view: untruncated section names, the percentage at each point, and a legend table pairing every section with its score. Closes on Escape, the backdrop, or the Close button, and returns keyboard focus to the expand button.
- Verified: `tests/test_dashboard.py` (the viewBox is computed, not a fixed constant; the expand button, modal, close paths and legend are wired; the exploded view uses the same theme colours as the tile rather than SVG's black default). Browser run against a fake 6-section assessment: zero clipped labels and symmetric margins on the tile, full labels and a correctly coloured chart in the exploded view, Escape closes it and returns focus, no console errors.

### Live DLP Feed: transactions landing live, with success/error and the reason
- **What you asked for.** "I want the ability to view the traffic as it traverses all policies in Zscaler in real time — vital to troubleshoot, must be interactive, and provide success or error rates and reasoning." You confirmed the API client has Insights access.
- **What Zscaler's API actually exposes, checked before building anything.** There is no pull API for the full ZIA transaction log (every URL Filtering, Cloud App Control and Firewall & DNS Control decision) — that data is Web Insights / Cloud NSS, a *push* feed to your own log store (Splunk, S3, a syslog receiver) that this tool cannot read. What the API does expose live is Workflow Automation's own DLP incident search, the same one the FP/TP Detection Ratio report already reads. **Find the gaps → Live DLP Feed** (`/report/live`) is built on that, honestly, with the gap stated on the page itself, not hidden.
- **What it does.** Start the feed and it polls every 15 seconds: the first poll looks back two minutes (never dumps history), every poll after only asks for what landed since the last one. Each row shows **who** was transacting, **what triggered** (the rule and dictionaries, with match counts), **where the data was headed** (URL host, application, or the recipients for mail), the channel, and — read from the rule's actual configured action, never guessed — whether it was **enforced** (blocked/confirmed) or only **monitored**. A running tally across the session: seen, enforced, monitor-only, still open, and the **FP:TP ratio** among the ones already verdicted. Stop any time; Reset session clears the tally and the rows.
- **Interactive and live**, per the ask: no page reload, a growing table with a soft highlight on new rows (skipped under `prefers-reduced-motion`), an accessible live region announcing new arrivals in a batch instead of one-by-one.
- Verified: `tests/test_detection_health.py` (the windowed fetch behind the poll, the moving `since` and the clamp on a stale one, the rule-action lookup used instead of guessing, the session tally rolling up across polls, the endpoint end to end, the page wiring). Browser run against a fake tenant that adds a fresh incident mid-session: the first poll shows the seeded incidents with correct enforced/monitor tags, the second real poll (15 s later) picks up the new one and flashes it in, Stop/Reset/Back all work, no console errors.
- Not built: the wider ZIA transaction log (URL Filtering/Cloud App Control/Firewall decisions with no DLP match). That needs your tenant's Cloud NSS pointed at a log store this app can read — a separate, larger integration; ask if you want it scoped.

### Path Analyzer: what to do about it, reasoned across every DLP channel
- **What you asked for.** "Take into account app profile bypasses heavily, and what should you choose to mitigate the risk — this accounts for Email, Endpoint DLP, SaaS CASB DLP and inline."
- **Now** every Path Analyzer result carries a **What to do about it, across every channel** section (`path_analyzer.recommend_mitigations`): a ranked, reasoned list, not a checklist. Whenever the network path itself sees nothing — bypassed by the app profile, or left encrypted by an SSL exemption — Endpoint DLP is weighed first, because it is the one control that runs on the device regardless of where the traffic goes: if it is off, that is the highest-severity fix; if it is already on, the page says so instead of suggesting nothing. Email DLP and SaaS Security API are recommended only when the destination is actually shaped like webmail (its ZIA category) or a sanctioned cloud application (ZIA's own lookup) — never as a blanket suggestion for an arbitrary site. A path that is already blocked, or already covered end to end, says plainly that there is nothing to mitigate.

### FP/TP Detection Ratio (was Detection Health): who is transacting, what triggered, where it was going, and the telemetry destinations to exclude
- **What you asked for.** The Detection Health page should analyse who is transacting, the triggers, and where the data was intended to be sent, so that publicly posted telemetry sites and URLs that never carry sensitive data can be excluded automatically; and the page should be the FP/TP detection ratio.
- **Now** the page is **FP/TP Detection Ratio** (same route, `/report/health`, same API). It opens with the ratio: every incident an analyst closed counts once, a resolution of *false positive / business justified / not an incident / not a violation / benign* is a false positive, any other closed incident a true positive, open incidents wait; shown as FP:TP in lowest terms (for example 6:1) with the share of verdicts that were not real and a one-line reading of what it means.
- **Every incident now carries who, what and where**: the user (as Workflow Automation records them, with department), the trigger (rule and the dictionaries with their match counts), the action (upload, post, send), the file, and the destination (the URL's host, the application, or for mail the recipients' domain). Three new sections: *Where it was going* (per destination: incidents, users, real, not real, actions, rules), *Who is transacting* (per user: incidents, real, not real, open, top destinations, rules) and *Latest transactions* (when, who, trigger, sent to, channel and action, verdict).
- **The exclusion algorithm.** A destination is marked **Exclude** when it has at least 3 incidents, none closed as real, and either its host or path matches a telemetry / public-content pattern (telemetry, metrics, analytics, beacon, crash and diagnostics collectors, Sentry / Datadog / New Relic / Segment / Mixpanel and the like, tag managers and ad beacons, update / OCSP / CRL services, `/v1/track`-style paths) or 80% or more of its closed incidents were not real. Each one becomes a finding and an **Exclude destination** proposal in the approval queue naming the rules it hits and the fix (a URL category or domain exclusion in the ZIA portal); nothing is written by itself, a person approves. The thresholds and the pattern list are settings (`dest_min_incidents`, `dest_fp_pct`, `telemetry_patterns`).
- The Markdown export carries the ratio and the two new tables. The report keeps user identities as the incidents carry them; it lives in the server's memory and is never written to disk.
- Verified: `tests/test_detection_health.py` (the new fields, the telemetry match, the exclusion decision, the users' and destinations' tables, the ratio, the proposal, the export). Not verified here: a real tenant's Workflow Automation feed.

### Path Analyzer: where a user's traffic to one destination goes, live, and what blocks or impacts it
- **What you asked for.** A built-in analyzer that takes an IP address or a URL and shows the path traffic takes through the tenant as if a user were browsing there, live, and clearly shows what blocks or impacts it.

The first run reads the tenant as it is right now (Client Connector app and forwarding profiles, trusted networks, PAC files, then SSL inspection, URL filtering, Cloud App Control, File Type Control, the DLP rules on every channel and the URL categories) with each step shown live, an elapsed clock and a Stop button; later runs reuse that read and only look the destination up, so they take seconds; *Fresh read* forces a new read. ### Tenant configuration: the classic ZIA API sign-in beside the ZIdentity API client
- **What was missing.** Every sign-in went through OneAPI: a ZIdentity API client (client ID, client secret, vanity domain). A tenant that has not enabled ZIdentity had no way in.
- **Now** Tenant Configuration has a *Sign-in method*: **OneAPI** (as before, the default) or **Classic ZIA API** (admin username, password and the tenant's API key from Administration → API Key Management, signed in at `zsapi.<cloud>.net` with the obfuscated-key session the classic API expects). The same nine credential fields travel in every request (`tenant_auth.py`), so the connection test, the assessment, Deploy Policy Packs, removals, Detection Health, the Terraform hand-off, the continuous evaluation, the MCP server and the command line all take either sign-in. Saved profiles keep the method and the username and remember the password and API key the way they remember a client secret (the OS credential store, else the owner-only file; never returned by the API, masked in every error, redacted in the audit log). ### Updater
- A half-applied earlier update (re-applying the edits conflicted, leaving "unmerged paths") no longer blocks every later update: the conflicted files are copied to `updater_backup\<timestamp>\`, the folder is reset to the last build and the update continues; the edits from that update remain in `git stash`.
- "Could not set aside the hand-edited files: error: could not write index" is handled: a stale `.git\index.lock` (left by an interrupted git) is removed automatically before the update, a lock that is only seconds old is left alone and explained, and the error now says what to check (editor/IDE, OneDrive or antivirus holding the folder, read-only `.git`).

### Detection Health (continuous evaluation, phase 1)
- New **Detection Health** report (toolbar tile, `/report/health`, `POST /api/detection-health`): what the tenant's DLP rules actually do, measured from Workflow Automation incidents and the analysts' verdicts. Per rule, engine, dictionary, channel, application and department: incidents, closed, not real and the false-positive rate; rules classified **noisy** (≥ 40 % not real over 14 days with ≥ 10 closed), **dead** (enabled, no incident in 30 days), **ready to promote** (monitor-only, ≤ 5 % not real over 30 days with ≥ 20 closed), healthy, disabled or not in the inventory; findings worst first. "Not real" defaults to False Positive / Business Justified / Not an incident / Not a violation / Benign; every threshold can be overridden per request (`settings`).
- The report says **how incidents reach Workflow Automation**: cloud-to-cloud forwarding (rules with Zscaler Incident Receiver), an on-premises Incident Receiver over ICAP, both, or neither — and names the enabled rules that forward nowhere, which is why a tenant can have matches but no incidents.
- Every 6 hours, for tenant profiles that remember their secret, the report runs on its own and a compact entry lands in the profile history (`GET /api/detection-health/schedule` shows the state). Read-only; no user identities are kept (departments and counts only). Markdown and JSON export.
- Traffic Flow's incident hop and reference diagram name both delivery paths.

### Deploy
- **Read back after writing.** After the objects are created and ZIA is activated, the deploy waits for ZIA to report ACTIVE and runs the same preflight again: every dictionary, engine and rule it created, overwrote, modified or reused must be found. The Done step shows "Verified by a fresh read: all N objects are in the tenant" or lists exactly what a fresh read could not find (`read_check` in the API result).
- **Endpoint DLP: one removable-media rule per engine.** Every pack now ships, besides the Endpoint mirror of each inline rule, one Endpoint DLP rule per engine scoped to removable media (`REMOVABLE_DRIVE_TRANSFER`, monitor-only, disabled, named `<engine> [Endpoint Removable Media]`), so incidents on USB and other removable drives name the engine and the control can be enabled engine by engine. `tools/fan_out_channels.py` generates them; Terraform regenerated.

### Removal
- **Verified by reading.** After the deletes and the activation, the removal polls ZIA until it reports ACTIVE (up to 45 s), then runs the same discovery the preview ran against the tenant. The wizard's new **Verify** step says "nothing of the pack remains" or lists exactly what is still there, with *Verify again* (a fresh read on demand) and *Remove leftovers* (runs the removal again on exactly those objects). A removal is only called complete when the read comes back clean.
- **Remove every deployed pack at once** now means everything DLP-Check ever put in the tenant: any object carrying a DLP-Check tag (whatever pack id or version wrote it — the retired CUI Marking and Endpoint packs included), plus the names of every pack in the library and of objects earlier pack versions shipped under other names (Fed 1.1's CUI engines and dictionaries, the endpoint pack's PCI engines and rules, the pre-v4.14 source-code objects, extension rules named after the old "Baseline" pack names). Same per-object rules as a single pack: anything a customer rule or engine still uses is kept and listed.
- **Pick rules to remove**: a third way in, for leftovers no tag or name can identify. The wizard lists every DLP rule in the tenant on every channel (state, engines, whether DLP-Check created it, with a filter and select-by helpers); tick the ones to remove and the plan adds the engines and dictionaries only they use, keeping anything an unticked rule or a surviving engine still uses, then preview → approve → remove → verify as usual. `POST /api/dlp-packs/removal/inventory` lists the rules; `rules: [{channel, id}]` on the preflight/apply endpoints selects them.
- Packs without a baseline section (Fed, CJIS) now tag every object they create (`[DLP-Check pack <id> v<version>]`), so a later removal finds them by tag instead of by name alone.
- SaaS Security API rules are now actually deleted: the delete call carries the rule's `ruleType`, which the API requires; without it every SaaS row failed.
- After the final activation the removal re-reads the tenant and reports any object it still lists as **still present** (the removal is not called complete until nothing is left), instead of trusting the delete calls.

### Traffic Flow & Gaps
- No more "Could not read" boxes. Traced paths draw only the data security controls (Cloud App Control, URL Filtering, SSL, File Type Control, DLP, then logs & incidents); Browser/FTP Control, threat protection, Bandwidth Control and Firewall & DNS are not data-leak controls and are left out of the path (the reference diagram still shows ZIA's full order). A Client Connector hop the tool cannot interpret says what it assumed and why ("no app profile for macos", "no forwarding profile linked", "mode 'X' not recognised for off network").
- The path now follows ZIA's policy enforcement order for a web request (Zscaler, *Understanding Policy Enforcement*): Browser & FTP Control, Cloud App Control before URL Filtering (URL Filtering is marked not evaluated when an app-control rule matched), SSL inspection, Malware Protection / Advanced Threat Protection, upload File Type Control, upload Bandwidth Control, Web DLP, Firewall & DNS Control last, then a "Logs & incidents" hop showing which rules forward to the Zscaler Incident Receiver / ICAP and notify an auditor, with a weak point when none do.
- A reference diagram at the top of the report, "How ZIA processes a policy: device → incident", in the same style as the traced paths, with an explanation per stage through Nanolog/NSS, the Incident Receiver and Workflow Automation.

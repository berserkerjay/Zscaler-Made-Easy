Data Security Architect

Zscaler's data-security reference architecture, module by module: how every DLP channel captures content, how dictionaries and engines decide, what a verdict produces, how evidence reaches Workflow Automation, what breaks when a setup step is skipped, and how to walk a symptom back to its cause. The diagrams and tables are the Architect team's own; this page carries them offline inside the tool so a gap on a flow page and its intended design sit one click apart.

Source: the team's Data Security Architect site (Google Sites, zscaler.com sign-in) — the live version changes there; this copy was taken on 2026-09-29.

00 The chain, end to end

Every Zscaler DLP channel is the same machine: content is captured, a dictionary reports a match count, an engine turns counts into a verdict, a channel rule acts on it, and the evidence has to be forwarded on purpose or Workflow Automation stays empty. Read this section first; every module below is one link of it.

01 Dictionaries

A dictionary is one detector for one kind of data. It outputs a match count, never a verdict. Pick the type by what it must recognise: a shape, your own records, your own documents, or Microsoft labels.

Common fields (all custom dictionaries)

NameFree text; shown in engines, logs, notification macros
Dictionary typeExact Data Match · Indexed Document Match · MIP · Patterns & Phrases — immutable after creation
DescriptionOptional

Save alone does nothing — every change needs Activate.

Org-level settings that silently change dictionary behaviour

OCRPer-channel toggles (Inline / SaaS API / Email) in DLP Advanced Settings — off means image files are never scanned, no dictionary ever sees them (PNG, JPEG, TIFF, BMP)
EDM variants"EDM with No Primary Keys" (requires deleting ALL existing EDM schema first) and "EDM Check for Popular Formats" (SSN/SIN/CCN strict format matching) — both in DLP Advanced Settings

02 Engines

An engine combines dictionaries with All / Any / Exclude / Sum and a strict "more than N" match count per dictionary. Its Channels gate decides which rule builders can even see it.

Common fields & builder rules

NameShown in rule builders, logs (dlpeng), notification macros
ChannelsMandatory multi-select — see the Channels gate above
Engine builderOperators All / Any / Exclude / Sum + dictionaries; live Expression Preview
DescriptionOptional, ≤ 255 characters
Root operatorAll / Any / Sum only — no Exclude at root
Per-level limits≤ 4 subexpressions · ≤ 4 operators · ≤ 16 dictionaries per operator
SumCount-based dictionaries only; select ≥ 2; match count required (< 1,000); cannot contain subexpressions
Match countStrict "> N"; < 1,000; the same dictionary may carry different counts in different engines
Parent / sub dictionariesEvaluate independently; container-only parents force a sub-dictionary selection
Custom engines≤ 512 per org

API-created engines & scanning limits

Cloud Service APIEngines can be created via API. Expressions the UI can't parse (e.g. (D63.S > 0 AND NOT D39.S > 0), SUM(D63.S, D246.S) > 2) display as a read-only Reference Expression with an empty builder — to edit in the UI you must manually recreate the expression
Scan limitsFiles ≤ 400 MB; first 100 MB of extracted text; archive members ≤ 100 MB; ≤ 5 compression levels (one rule-form help text says 100 MB — verify)
TimeoutInline scan timeout fails open — logged only as exempt_dlpidentifier (module 03)

Downstream: every channel's rule references ≤ 4 engines (or Any). "All the dictionaries in a given engine must trigger for an engine to trigger" applies to All-operator expressions — the #1 accidental "both must appear" build. Rule-level Match Only (inline) additionally requires that no other rule's engines matched.

03 Inline Web DLP

The gauntlet: what gets seen, what blocks before DLP ever runs, and what a verdict produces. This is the module the tool's Traffic flow & gaps, Path analyzer, SSL inspection flow and Bypass pages measure a tenant against.

What never reaches DLP (stops earlier)

Firewall blockTraffic never enters the web module (but Firewall logs show web-blocked traffic as allowed — logging asymmetry)
Any web blockCustom malicious URL · CAC block (incl. blocked upload activity or wrong tenant) · URL Filtering block or exhausted quota · Browser Control · ATP · Malware
FTC blockSilently pre-empts DLP — verbatim: "the DLP policy itself is never triggered, and the service does not send a notification alerting the auditor"
Not decryptedDo-Not-Inspect (either flavour), exemption lists, or no user context at CONNECT/SNI → payload invisible, DLP impossible

What still reaches DLP (continues)

CAC allowSkips URL Filtering only — the POST chain continues through Malware → FTC → DLP. Cascading re-inserts URLF; it never affects DLP
Security exceptionsSkip Malware + ATP + Sandbox only — FTC and DLP still run
Post-caution uploadsCaution exists only on GET/HEAD; when the user clicks through, the subsequent POST runs the full chain including DLP
Isolation egressRe-enters ALL policy (target it via Device Group "Cloud Browser Isolation") — plus in-session DLP-engine redaction and controlled file transfer

Tenant-profile gotcha: allowing a tenant auto-blocks all others AND stops further policy — except YouTube and AWS, where later policies still evaluate and an explicit block rule is required.

04 Endpoint DLP

Detection content is built in the cloud and pushed to the device; the ZDP module intercepts activity, evaluates ALL rules (most restrictive wins), inspects on-device and logs locally, then the same evidence chain as every other channel.

Signature gotchas (field checklist)

Two enginesDevice Control = sequential first-match (default rule disabled = ALL DC rules off); Endpoint DLP = all-rules / most-restrictive. Two policy versions tracked per endpoint, two activation planes (ZIA portal + Data Scan portal)
ClassificationContinuous Classification is SSD-only by default — HDD estates are blind until toggled (surfaces as a DLP Operational action item). Real-time classification timeout (15–120 s) defaults to Allow
macOS scopePrint = monitor-only; Confirm-on-print can't cancel; iCloud is the macOS-only personal cloud
Printing detailWithout the Office add-ins, only spooled text is inspected — no MIP labels or file metadata. Print OCR is Windows-only; EDM printing needs Office / Adobe
Audit gapsException action "None" allows without logging — by design. Printer / File-Save exceptions can be Monitor Only
Scope limitsEDM not supported on Clipboard · Application File Access blocks at file-open only (never use on browsers / email clients) · Protect is not for long-term backup · gated features: App File Access, Clipboard, app resources, Endpoint IDM

05 Email DLP

Zscaler is an inline smart host that tags; your mail platform enforces. Without a header-enforcement transport rule it is silent monitor-only, and without loop prevention inspected mail is re-sent to Zscaler forever.

Gotchas that define this channel

Silent monitor-onlyZscaler only inserts headers. If Exchange / Gmail has no transport rule matching X-Zscaler-Block: 1 (or the quarantine header), everything is tagged and delivered — the #1 email-channel miss
Mail loopsThe return leg re-enters your outbound flow. Without loop prevention (Exchange Except-if on the Zscaler headers; Gmail source-IP exclusion), inspected mail is re-sent to Zscaler forever
Per-recipient evaluationRules evaluate per recipient, most restrictive wins, and Block always beats Quarantine. Quarantine is an Exchange-only action — on Gmail it does nothing
Propagation & plumbingGmail content-compliance changes take up to 24 h to apply. The tenant-ID header must be stamped or the smart host cannot match your tenant. Auditor email needs BOTH an auditor and a template selected — either missing is silent
Incident managementSame pipeline as inline web: per-rule ZIR / C2C forwarding → your -metadata / -data buckets → Workflow Automation (Source: Email) — and unlike endpoint, WA policy exceptions ARE available for email

06 SaaS Security API and SSPM

Out of band, nothing inline: API scans crawl content at rest in your sanctioned tenants; a scan configuration must exist, reference at least one policy and be started by hand, or nothing scans. SSPM is the posture side of the same onboarding.

Gotchas that define this channel

Nothing scans by itselfPolicies do nothing until a Scan Configuration exists, references at least one policy, and is manually started. "Scan Initialized" means prerequisites are still being verified — not scanning
Tenant health is silentStatus must be Active. Validation Failed or Reauthorization Required (an admin role removed, a licence lost) silently stops all scanning until fixed
Cutoff-date resetAdding or editing any policy rule while a scan runs resets the active / historical cutoff to the edit date — already-processed content becomes historical
Scope trapsOne provider per rule; sites and site groups are mutually exclusive; trusted users / domains make matches "internal" and suppress incidents. Per-app data windows vary (Webex 15-day cap; historical reach ≤ 6 years)
Public-cloud malware quirkBucket selection is circular: save the rule → create the scan schedule → reopen the rule to pick buckets. A rule saved without buckets scans nothing
Incident managementSame pipeline: per-rule C2C forwarding → your -metadata / -data buckets → Workflow Automation (Source: SaaS). Policy exceptions are NOT available for SaaS — that lever exists only for Inline and Email

07 EDM and IDM

Exact Data Match fires only on records you indexed; Indexed Document Match fires on whole or partial copies of documents you fingerprinted. Both are built on a customer-hosted Index Tool VM; raw data stays on your premises and only hashes leave.

08 AI security

Three parts: thick-client AI agents on the endpoint (Endpoint DLP controls the clipboard and file access), secure access to AI apps inline (the same gauntlet, then a forwarding-control hop to AI Guard), and AI Guard's own prompt and response detectors.

A prompt
ZCC → ZIA (IdP-authenticated) → the full inline stack (CAC, Threat Protection, Web DLP "still occur here"; inline DLP can fire on the POST body) → Forwarding Control proxy-chains matching AI domains to forward.zseclipse.net:9443 (fail close, AI Guard CA trust, X-Authenticated-User identity, QUIC blocked) → AI Guard: Policy Controls first-match (LLM provider / models · users / groups · Account Type), then the matched configuration's prompt detectors each vote Allow / Block / Detect → blocked = custom message in place (delivered via the LLM — may misinterpret), optional conversation delete, Reveal → Allowlist → not blocked: AI Guard originates the LLM connection → the response passes response detectors → back through ZIA to the user.
A file
Same hops — but the judgment happens at hop 1: inline Web DLP (Inline-channel engines) inspects the upload; Block ends it with the normal EUN, and incidents ride the classic chain (auditor · ZIR / C2C → buckets → Workflow Automation). An allowed file then transits AI Guard as passthrough — the secure-ai-users docs define detectors for prompts and responses only, no file inspection. AI-level control of files = control the app, tenancy, and the prompt around it.
Two detection brains
Hop 1 uses ZIA DLP engines / dictionaries (Common Resources). Hop 2 uses AI Guard's own detectors (PII, Secrets, Code, Text-regex, Injection / Jailbreak, Topic, IP, Competition…) with severity / threshold / action per detector. Nothing is shared between them.
Two consoles, two log worlds
ZIA logs the forwarding transaction in Web Insights and file incidents flow to WA as usual. AI Guard's prompt / response telemetry lives in its own portal (90-day store toggle, Dashboard / Insights) with native exports (S3, Splunk, CrowdStrike, ADX) — no NSS feed, no WA integration documented.
Tenancy restriction
Register your Anthropic Org IDs / OpenAI Workspace IDs; runtime traffic tagging marks matches Enterprise and everything else Personal, and Account Type becomes a policy-control criterion — e.g. strict detectors on Personal, lighter on Enterprise.
Prereqs
AI Guard subscription · ZIA ↔ AI Guard linked by Zscaler Support · Experience Center enabled · the AI Guard CA uploaded as a Proxy Chaining root certificate · supported app domains in the Wildcard FQDN group.

09 Workflow Automation

Incidents exist only when every channel rule forwards evidence to storage the integration was validated against. Then: the incident lifecycle, the workflow builder, and the nine use cases the team runs.

10 Setup sequences (what breaks if you skip a step)

Condensed lifecycles per channel. The highlighted steps are the gates people miss. Full detail with console paths lives in the reference files.

Universal first: detection building blocks
  1. EDM / IDM only: Index Tool config in Admin Console → deploy Index Tool VM → template reaches Completed. Skipped → the dictionary type can't even be created.
  2. Create DLP dictionaries (Patterns & Phrases / EDM / IDM / MIP) — confidence thresholds live here.
  3. Build DLP engines (Boolean expression, match counts are strict "> N") and set each engine's Channels.
  4. Create notification templates; create auditors. A rule needs BOTH auditor and template or no email is ever sent.
  5. Deploy Zscaler Incident Receiver or configure Cloud-to-Cloud Forwarding before building rules that should feed Workflow Automation.
  6. Check DLP Advanced Settings: OCR per channel, exemption lists (they override rules), evaluation mode.
  7. Activate. Saved ≠ active.
Inline Web DLP
  1. Traffic forwarding + user provisioning (ZCC / tunnels / PAC).
  2. Enable SSL/TLS inspection and confirm target traffic is actually decrypted. Skipped → DLP never sees HTTPS payloads.
  3. Build the DLP rule (engines ≤ 4, criteria are AND-ed; users / groups / departments OR-ed).
  4. Select Incident Receiver / C2C on the rule if incidents should reach Workflow Automation. The most-missed link.
  5. Set auditor + template; EUN show / hide; activate.
  6. Remember policy order: File Type Control and Cloud App Control run before DLP on POSTs.
Endpoint DLP
  1. Verify platforms (Win 10 2004+ / 11 64-bit, no ARM; macOS 14+; ZCC 4.3 / 4.2+); allowlist ZDP in AV / EDR.
  2. macOS: push Full Disk Access via MDM before Endpoint DLP installs.
  3. Create Endpoint Resources (printers, USB by VID / PID / serial, shares) + tags — required for per-device targeting and exceptions.
  4. Build endpoint rules (channel, engines ≤ 4, actions Allow / Block / Confirm / Protect; ≤ 32 exceptions).
  5. Enable "Install Endpoint DLP" in the ZCC app profile. Skipped → cloud policy, zero enforcement.
  6. Wait for the 15-min policy pull (or force update); configure NSS feeds if SIEM export is wanted.
Email DLP
  1. Domains in Company Profile (feeds the tenant's domain dropdown).
  2. Add Email Tenant → copy Smart Host FQDN + Key for Transport Rules; set per-domain next hop.
  3. Platform side: connectors / route to smart host + tenant-ID header + loop prevention + header-enforcement rules. No enforcement rule → silent monitor-only. No loop guard → mail loop.
  4. Domain / recipient profiles for recipient scoping.
  5. Outbound Email Policy rules (per-recipient, most restrictive; Quarantine = Exchange only).
  6. Flip platform rules from test to Enforce last. Gmail changes propagate up to 24 h.
SaaS Security API / SSPM
  1. Onboard the SaaS tenant — the "Onboard for" checkboxes (DLP / Malware vs SSPM vs Workflow Automation) fork everything downstream; file apps need a quarantine location at onboarding.
  2. Per-platform authorization (M365 Global Reader on the connector ID; Google Cloud Identity licence; S3 IAM role + CloudTrail + quarantine bucket…).
  3. Create Data-at-Rest DLP and / or Malware rules (tombstone template required for quarantine actions).
  4. Create a Scan Configuration (1 per tenant, ≥ 1 policy) and press Start. No scan → policies do literally nothing.
  5. Watch the cutoff quirk: editing any rule mid-scan resets the active / historical cutoff date; stopping a scan flushes its queue.
Workflow Automation
  1. Grant ZIA admins the Workflow Access permission.
  2. Build the DLP Application Integration: storage buckets (-data / -metadata, same region as SNS topic, names without dots) + notification topic + cross-account role → Validate → Enable.
  3. Point every channel rule at the ZIR / C2C config that writes to that storage. The #1 cause of the empty console.
  4. Incident groups + mappings + default group; priorities; approvers; admin assignments.
  5. Import user attributes (SCIM / CSV) — manager escalation depends on it.
  6. Build workflows from templates and publish them (unpublished workflows never fire); map to incident attributes.

11 Symptom → dependency walkbacks

Each symptom is a broken link somewhere upstream. Steps are ordered by hit-rate: walk the chain backward.

Workflow Automation shows no incidents canonical
  1. Integration health: does the DLP Application Integration exist and show Enabled (not Failed)?
  2. Rule forwarding: do source-channel rules actually select a ZIR or C2C config? NSS feeds, auditor email, and third-party ICAP never feed WA.
  3. Same storage? The rules' forwarding target must write to the buckets the integration was validated against.
  4. Storage plumbing: AWS — metadata bucket + SNS topic same region, ObjectCreated wired; names ≤ 40 chars, no dots. Azure — Event Grid topic, NAT IPs allowlisted.
  5. ZIR health (if used): VM up, cert installed, ICAP port open to Zscaler's FCC cloud, SFTP / S3 storage writable (ZIR stores nothing locally).
  6. One channel missing? Forwarding is selected per rule — normal for endpoint incidents to arrive while email doesn't.
  7. Not ingestion at all: restricted admins only see their assigned incident groups.
Inline web rule never fires
  1. SSL inspection on, and this traffic actually decrypted (not exempted)? — cause #1.
  2. DLP Advanced Settings exemptions (apps / URLs / categories) override every rule.
  3. Policy-order pre-emption: File Type Control / Cloud App Control / URL Filtering block ends evaluation before DLP.
  4. Criteria AND-logic: engines ∧ file type ∧ users ∧ location ∧ protocol… Downloads need Inspect Downloads (excludes EDM / IDM).
  5. Engine internals: match count is "> N"; All-operator needs every dictionary; dictionary confidence too high.
  6. Content: OCR off → images never scanned; size limits; scan timeout fails open (check Exempted DLP Identifier in Web Insights).
  7. First-match shadowing by an earlier rule (even an Allow). And: activated, not just saved?
Endpoint DLP not enforcing on a device
  1. ZDP module installed? ("Install Endpoint DLP" in the ZCC app profile — check the device's Data Protection window.)
  2. Platform support: no Windows ARM; macOS Full Disk Access pushed before install; minimum ZCC versions.
  3. Policy sync: 15-minute pull; force with Update DLP Policy.
  4. Active 12-hour OTP exemption on the device (works offline).
  5. Resource targeting mismatch (USB VID / PID / serial, printer identity).
  6. Engine missing the Endpoint DLP channel; parent / sub dictionaries unsupported on endpoint.
  7. Evaluation surprise: ALL rules evaluated, most restrictive wins — an Allow exception on one rule doesn't stop another rule.
  8. AV / EDR quarantined the ZDP module (allowlist paths).
Email DLP blocks nothing (tagged but delivered)
  1. Enforcement is delegated: is there a platform rule matching X-Zscaler-Block: 1? Without it: silent monitor-only.
  2. Is mail reaching the smart host at all (connector / route present and enforced; Gmail propagation up to 24 h)?
  3. Tenant-ID header stamped with the Key for Transport Rules?
  4. Return path accepted (Exchange receive connector / Gmail SMTP-relay IP allowlist from config.zscaler.com)?
  5. Loop prevention present (Except-if on X-Zscaler-Block / source-IP-not-in-range)?
  6. Quarantine is Exchange-only and its header must be mapped; Block always beats Quarantine.
SaaS API scan finds nothing
  1. Does a scan exist, reference ≥ 1 policy, and was it started? "Scan Initialized" is still prereq-checking.
  2. Tenant status Active? Validation Failed / Reauthorization Required = scanning silently stopped.
  3. Data window: "New Data Only" scans nothing historical; per-app caveats (Webex 15-day cap, Zoom features).
  4. Rule targeting: one provider per rule; trusted users / domains suppress matches as "internal".
  5. Cutoff reset: any rule edit mid-scan moves the active / historical cutoff to the edit date.
  6. Public-cloud malware circularity: save rule → create schedule → reopen rule to pick buckets.

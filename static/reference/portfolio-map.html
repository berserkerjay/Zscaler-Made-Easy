The portfolio's first split: data in motion vs data at rest

Every channel belongs to one of two enforcement models — and the difference is the verb: in-motion channels can block before data leaves; at-rest channels remediate what's already there.

The verdict happens during the transaction — the data can be stopped before it leaves.

Order of operations

Setup sequences (what breaks if you skip a step)

Condensed lifecycles per channel. Amber-numbered steps are the gates people miss. Full detail with console paths lives in the reference files.

Universal first: detection building blocks
  1. EDM/IDM only: Index Tool config in Admin Console → deploy Index Tool VM → template reaches Completed. Skipped → the dictionary type can't even be created.
  2. Create DLP dictionaries (Patterns & Phrases / EDM / IDM / MIP) — confidence thresholds live here.
  3. Build DLP engines (Boolean expression, match counts are strict ">N") and set each engine's Channels.
  4. Create notification templates; create auditors. A rule needs BOTH auditor and template or no email is ever sent.
  5. Deploy Zscaler Incident Receiver or configure Cloud-to-Cloud Forwarding before building rules that should feed Workflow Automation.
  6. Check DLP Advanced Settings: OCR per channel, exemption lists (they override rules), evaluation mode.
  7. Activate. Saved ≠ active.
Inline Web DLP
  1. Traffic forwarding + user provisioning (ZCC / tunnels / PAC).
  2. Enable SSL/TLS inspection and confirm target traffic is actually decrypted. Skipped → DLP never sees HTTPS payloads.
  3. Build the DLP rule (engines ≤4, criteria are AND-ed; users/groups/departments OR-ed).
  4. Select Incident Receiver / C2C on the rule if incidents should reach Workflow Automation.
  5. Set auditor + template; EUN show/hide; activate.
  6. Remember policy order: File Type Control and Cloud App Control run before DLP on POSTs.
Endpoint DLP
  1. Verify platforms (Win 10 2004+/11 64-bit, no ARM; macOS 14+; ZCC 4.3/4.2+); allowlist ZDP in AV/EDR.
  2. macOS: push Full Disk Access via MDM before Endpoint DLP installs.
  3. Create Endpoint Resources (printers, USB by VID/PID/serial, shares) + tags — required for per-device targeting and exceptions.
  4. Build endpoint rules (channel, engines ≤4, actions Allow/Block/Confirm/Protect; ≤32 exceptions).
  5. Enable "Install Endpoint DLP" in the ZCC app profile. Skipped → cloud policy, zero enforcement.
  6. Wait for the 15-min policy pull (or force update); configure NSS feeds if SIEM export is wanted.
Email DLP
  1. Domains in Company Profile (feeds the tenant's domain dropdown).
  2. Add Email Tenant → copy Smart Host FQDN + Key for Transport Rules; set per-domain next hop.
  3. Platform side: connectors/route to smart host + tenant-ID header + loop prevention + header-enforcement rules. No enforcement rule → silent monitor-only. No loop guard → mail loop.
  4. Domain/recipient profiles for recipient scoping.
  5. Outbound Email Policy rules (per-recipient, most restrictive; Quarantine = Exchange only).
  6. Flip platform rules from test to Enforce last. Gmail changes propagate up to 24 h.
SaaS Security API / SSPM
  1. Onboard the SaaS tenant — the "Onboard for" checkboxes (DLP/Malware vs SSPM vs Workflow Automation) fork everything downstream; file apps need quarantine location at onboarding time.
  2. Per-platform authorization (M365 Global Reader on the connector ID; Google Cloud Identity license; S3 IAM role + CloudTrail + quarantine bucket…).
  3. Create Data-at-Rest DLP and/or Malware rules (tombstone template required for quarantine actions).
  4. Create a Scan Configuration (1 per tenant, ≥1 policy) and press Start. No scan → policies do literally nothing.
  5. Watch the cutoff quirk: editing any rule mid-scan resets the active/historical cutoff date; stopping a scan flushes its queue.
Workflow Automation
  1. Grant ZIA admins the Workflow Access permission.
  2. Build the DLP Application Integration: storage buckets (-data/-metadata, same region as SNS topic, names without dots) + notification topic + cross-account role → Validate → Enabled.
  3. Point every channel rule at the ZIR/C2C config that writes to that storage. The #1 cause of the empty console.
  4. Incident groups + mappings + default group; priorities; approvers; admin assignments.
  5. Import user attributes (SCIM/CSV) — manager escalation depends on it.
  6. Build workflows from templates and publish them (unpublished workflows never fire); map to incident attributes.

Walk the chain backward

Symptom → dependency walkbacks

Each symptom below is a broken link somewhere upstream. Steps are ordered by hit-rate.

Workflow Automation shows no incidents canonical
  1. Integration health: does the DLP Application Integration exist and show Enabled (not Failed)?
  2. Rule forwarding: do source-channel rules actually select a ZIR or C2C config? NSS feeds, auditor email, and third-party ICAP never feed WA.
  3. Same storage? The rules' forwarding target must write to the buckets the integration was validated against.
  4. Storage plumbing: AWS — metadata bucket + SNS topic same region, ObjectCreated wired; names ≤40 chars, no dots. Azure — Event Grid topic, NAT IPs allowlisted.
  5. ZIR health (if used): VM up, cert installed, ICAP port open to Zscaler's FCC cloud, SFTP/S3 storage writable (ZIR stores nothing locally).
  6. One channel missing? Forwarding is selected per rule — normal for endpoint incidents to arrive while email doesn't.
  7. Not ingestion at all: restricted admins only see their assigned incident groups.
Inline web rule never fires
  1. SSL inspection on, and this traffic actually decrypted (not exempted)? — cause #1.
  2. DLP Advanced Settings exemptions (apps/URLs/categories) override every rule.
  3. Policy-order preemption: File Type Control / Cloud App Control / URL Filtering block ends evaluation before DLP.
  4. Criteria AND-logic: engines ∧ file type ∧ users ∧ location ∧ protocol… Downloads need Inspect Downloads (excludes EDM/IDM).
  5. Engine internals: match count is ">N"; All-operator needs every dictionary; dictionary confidence too high.
  6. Content: OCR off → images never scanned; size limits; scan timeout fails open (check Exempted DLP Identifier in Web Insights).
  7. First-match shadowing by an earlier rule (even an Allow). And: activated, not just saved?
Endpoint DLP not enforcing on a device
  1. ZDP module installed? ("Install Endpoint DLP" in the ZCC app profile — check the device's Data Protection window.)
  2. Platform support: no Windows ARM; macOS Full Disk Access pushed before install; minimum ZCC versions.
  3. Policy sync: 15-minute pull; force with Update DLP Policy.
  4. Active 12-hour OTP exemption on the device (works offline).
  5. Resource targeting mismatch (USB VID/PID/serial, printer identity).
  6. Engine missing the Endpoint DLP channel; parent/sub dictionaries unsupported on endpoint.
  7. Evaluation surprise: ALL rules evaluated, most restrictive wins — an Allow exception on one rule doesn't stop another rule.
  8. AV/EDR quarantined the ZDP module (allowlist paths).
Email DLP blocks nothing (tagged but delivered)
  1. Enforcement is delegated: is there a platform rule matching X-Zscaler-Block: 1? Without it: silent monitor-only.
  2. Is mail reaching the smart host at all (connector/route present and enforced; Gmail propagation up to 24 h)?
  3. Tenant-ID header stamped with the Key for Transport Rules?
  4. Return path accepted (Exchange receive connector / Gmail SMTP-relay IP allowlist from config.zscaler.com)?
  5. Loop prevention present (Except-if on X-Zscaler-Block / source-IP-not-in-range)?
  6. Quarantine is Exchange-only and its header must be mapped; Block always beats Quarantine.
SaaS API scan finds nothing
  1. Does a scan exist, reference ≥1 policy, and was it started? "Scan Initialized" is still prereq-checking.
  2. Tenant status Active? Validation Failed / Reauthorization Required = scanning silently stopped.
  3. Data window: "New Data Only" scans nothing historical; per-app caveats (Webex 15-day cap, Zoom features).
  4. Rule targeting: one provider per rule; trusted users/domains suppress matches as "internal".
  5. Cutoff reset: any rule edit mid-scan moves the active/historical cutoff to the edit date.
  6. Public-cloud malware circularity: save rule → create schedule → reopen rule to pick buckets.
No auditor email / EDM dictionary won't match

Auditor email: the rule needs BOTH an auditor and a template — either missing means no email, and the rule saves without warning. Then check TLS support and 25 MB attachment cap.

EDM: template must be Completed in the Index Tool; '.' is a numeric delimiter (delimited formats like ddd.ddd.ddd-dd don't match); blank cells never match; strings <3 chars ignored; fields/primaries immutable after creation — recreate, don't edit. Inline "Inspect Downloads" never applies to EDM/IDM.

DS-000 · Read this first — a program, not a product install

This curriculum teaches you a product portfolio, but the job it prepares you for is running a data-security program. The difference matters from the first unit. A product install has an end date: licenses activated, policies created, project closed. A program has a heartbeat: discover what data matters and where it lives → build detection for it → monitor without blocking → tune with real evidence → enforce → operate the incidents → expand to the next channel or data class — and then the loop runs again. Every level of this course maps onto that arc: DS-100 is the detection core, DS-200 is per-channel deployment and incident operations, DS-300 is posture, whole-org design, and migration.

Second: order of operations is not bureaucracy here — it is the architecture. A rule cannot exist without an engine; an engine cannot exist without dictionaries; an incident cannot exist without a per-rule forwarding choice; a channel cannot see data its gates never admitted. The portfolio is literally a dependency chain, so you build left to right and debug right to left. When something "doesn’t work," the question is never "why is the product broken" — it is "which link in the chain is missing," and this course drills that reflex until it is automatic.

Third: monitor before you block — always. You cannot tune what you never observed, and the fastest way to lose executive sponsorship is a week-one false-positive storm that blocks the CFO’s legitimate work. Every channel gives you a no-harm mode: inline rules can Allow while still notifying auditors and forwarding incidents; email with no enforcing transport rules tags everything and delivers everything; the endpoint has rule-free activity tracking and monitor-mode rules; SaaS API families all include report-only actions. A healthy program spends weeks in monitor mode per channel, reviews the evidence with data owners, tunes the engines, and only then turns enforcement on — deliberately, one channel at a time.

A legacy rule export is years of accumulated workarounds for a different engine with different semantics — porting it means importing the dirt while losing the context that made it make sense. 100.1 · The portfolio at 30,000 feet — two families, one detection core

Goal: name the five DLP channels and the posture family, and say which shared objects tie them together.

The portfolio splits into two families that answer two different questions. Content inspection answers "is sensitive data moving somewhere it shouldn’t, right now?" — it looks at actual bytes (an upload, a file on a laptop, an outbound email, a document at rest in OneDrive) and produces per-file verdicts and incidents. Posture answers "are the platforms that HOLD our data configured safely?" — it assesses tenants and clouds and produces findings, statuses, and risk scores, never per-file incidents. Mixing those outputs up is the most common early mistake: expecting DSPM or SSPM to raise a "DLP incident" leads you to hunt for a pipeline that was never supposed to exist.

What makes this a portfolio instead of five products is the shared detection core. You describe a kind of sensitive data once — dictionaries assembled into engines — and that ONE description is what the browser upload path, the laptop’s USB port, the outbound mail flow, and the SaaS-tenant scanner all consult. Build "customer PAN data" today for inline, and tomorrow’s endpoint rollout reuses it untouched. Detection compounds; only enforcement is per-channel.

From day one, hold the vocabulary discipline, because each verb belongs to exactly one object: the dictionary matched 12 card numbers; the engine fired because the count beat its threshold; the rule acted with Block; the channel enforced it in the browser. Four verbs, four objects, four different places to look when something misbehaves. Every troubleshooting method in DS-300 starts by asking which of the four actually failed — engineers who blur the verbs end up "fixing" the wrong layer.

Hold these facts

  • Family 1 — content inspection: Inline Web, Endpoint, Email, SaaS API. (Public AI Security is a separate three-part conversation — endpoint controls + the inline stack + AI Guard — with its own course tab.) One detection core; per-channel enforcement.
  • Family 2 — posture: SSPM & 3rd-Party App Governance (SaaS configuration + OAuth apps) and DSPM (data at rest in your clouds). Output = status & risk, never per-file incidents.
  • Detection is built once (dictionaries → engines); incidents travel a separate pipeline. That sentence is the whole map.
  • Consoles you will live in: the ZIA Admin Portal (detection + channel policy), the Workflow Automation portal (incidents), the 3rd-Party App Governance portal (SSPM), and DSPM inside the unified Admin Console.
  • Vocabulary discipline from day one: a dictionary matches, an engine fires, a rule acts, a channel enforces — four different verbs, four different objects.

100.2 · Dictionaries — teach the service what data looks like

Goal: pick the right dictionary type for a data description, and explain what a dictionary outputs.

A dictionary is a reusable description of what ONE kind of sensitive data looks like — nothing more. It is not a policy, it carries no opinion about blocking, and nothing in the product references it directly except engines. When content passes through, the dictionary answers a single question: how many things matching my description are in here? "This file contains 12 things shaped like credit-card numbers" is a complete dictionary answer. Whether 12 is a catastrophe or Tuesday is deliberately not its call.

Why counts instead of verdicts? Because context decides harm, and the dictionary has no context. One SSN in an email signature block is noise; five thousand in a CSV heading to a personal drive is a breach. The same description serves both cases — the threshold lives upstream in the engine, where you can set ">0" for a strict-compliance engine and ">100" for a bulk-exfiltration engine using the very same dictionary. This split — dictionaries describe, engines decide — is THE design idea of the whole detection core. Internalize it here and every later unit gets easier.

The working order matters: predefined first. Roughly 120 predefined dictionaries ship with tuned logic you cannot see, let alone reproduce — use them as-is, adjust confidence where offered, clone (up to 4 per predefined) when you need a variant, and only then build custom. The custom ladder is really a cost ladder: Patterns & Phrases costs nothing but regex skill; EDM/IDM buys precision on YOUR actual records and documents at the price of an Index Tool VM you must host and feed (DS-200.1); MIP costs a Microsoft tenant integration. And two quiet traps: OCR is a per-channel gate — leave it off for a channel and image files are simply never scanned there, with no error anywhere; and your regex runs as POSIX-ERE syntax on a Hyperscan-based streaming engine, which is why capture groups and backreferences don’t exist here no matter how fluent your PCRE habits are.

Hold these facts

  • Always check the ~120 predefined dictionaries first: use → tune confidence → clone (≤4) before building custom.
  • Patterns & Phrases mechanics: ≤8 patterns, ≤512 phrases, proximity windows, the per-channel OCR gate.
  • A dictionary outputs a MATCH COUNT — never a verdict. Nothing references a dictionary directly; engines do.
  • Custom types and their infrastructure bill: Patterns & Phrases (none) · EDM/IDM (Index Tool VM) · MIP (Microsoft tenant integration).
  • Proximity windows exist only in Patterns+Phrases mode; capture groups and backreferences are silently unsupported in patterns.
  • You write POSIX-ERE syntax, but a Hyperscan-based library executes it (ref-arch, verbatim) — the no-captures/no-backreferences limits are that engine’s signature, chosen for line-rate streaming inspection.

Field numbers: ~120 predefined · ≤4 clones each · ≤8 patterns · ≤512 phrases per dictionary · OCR formats: PNG · JPEG · TIFF · BMP

100.3 · Engines — where counts become decisions

Goal: read an engine expression and predict exactly when it fires.

The engine is the decision layer: it takes match counts from its dictionaries and turns them into a fired/didn’t-fire answer using boolean logic. Walk one example and the mechanics stick. An engine holds Credit Cards >3 AND US SSN >0. A spreadsheet arrives carrying 4 card numbers and 1 SSN: Credit Cards answers 4 (>3 ✓), SSN answers 1 (>0 ✓), All-mode requires every leg true — the engine fires. Same spreadsheet with 3 cards? 3 is NOT greater than 3 — safe. That strict ">" burns everyone exactly once: a threshold of N means N is safe and N+1 fires. Say "fires above three," never "fires at three," and you will not write the off-by-one engine that ships a breach.

Three combination modes, one distinction: All = every dictionary leg must clear its own threshold (AND); Any = one leg clearing suffices (OR); Sum pools the raw counts into one total judged once — 4 cards + 2 SSNs = 6 against a single ">5". Sum is how you express "I don’t care which kind, I care how MUCH." The same counts produce different outcomes under each mode, which is why the Prove-it below exists.

Two design habits to form now. First, the Channels gate: every engine declares where it may even be selected (inline, email, SaaS, endpoint — endpoint’s entry is a plain allow, no sub-configuration), and the gate is sticky — you cannot remove a channel while an active policy uses the engine, so plan gates before policies accumulate. Second, name engines by intent, not contents: a rule author choosing from a dropdown two years from now needs "PCI-bulk-exfil" and "PCI-strict-compliance," not "CC-SSN-engine-2". The engine name is the API between the detection team and the policy team.

Hold these facts

  • Each dictionary entry carries its own strict ">N" — count 6 with threshold 6 is SAFE; it fires at 7.
  • All = AND, Any = OR across the per-dictionary answers; Sum pools counts into one total judged once.
  • The Channels gate on the engine decides where it can even be selected — endpoint's entry is a plain allow.
  • An engine’s channel gate is sticky: a channel cannot be removed while an active policy uses the engine — plan gates before policies accumulate.
  • Predefined engines exist too (66 in DSPM’s catalog; ZIA ships its own variants) — same rule: check before building.

Field numbers: match-count values <1,000 · ≤4 engines per rule (inline · email · SaaS) · count N is SAFE, N+1 fires

100.4 · Your first inline rule — and everything that runs before it

Goal: build a mental model of the inline gauntlet: what must be true before DLP ever sees a byte.

The humbling truth of inline DLP: most "DLP isn’t working" cases have nothing to do with DLP. Follow one upload’s journey and you’ll see why. The browser opens TLS; the FIRST decision is SSL inspection — if the destination is exempted or bypassed, Zscaler sees only a domain name, forever, and no DLP rule will ever evaluate that traffic no matter how perfect the rule is. Survive that, and the upload still runs a gauntlet of policies that all execute BEFORE data protection: firewall control, Cloud App Control, URL Filtering, File Type Control — and any block among them ends the transaction on the spot. Ended early is ended: a File Type Control block produces NO DLP incident and NO auditor email, because DLP was never consulted. The transaction died healthy. This is the trap behind half of all empty-console mysteries: every channel working perfectly, and the console empty.

Only past the gauntlet do your rule’s own mechanics matter, and there are three: criteria AND together (engines AND file types AND users AND locations AND protocols — every leg must match, so each extra criterion narrows the rule); evaluation is first-match by default (an early Allow shadows everything below it — DS-200.5 teaches the alternative); and the scan timeout fails OPEN, logged with an exempt identifier — by design, availability beats inspection.

Program habit from the very first rule: start in monitor. Broadest sane criteria, action Allow, but auditor notification and incident forwarding ON. You now observe real traffic against real detection without user impact — a week of that tells you whether the engine threshold is sane before the first user ever sees a block page. Blocking on day one with untuned engines is how data-security programs get their executive sponsorship revoked.

Hold these facts

  • SSL inspection is dependency #1 — DLP never evaluates uninspected HTTPS.
  • Policy order: CAC, URL Filtering, File Type Control run first; an earlier block means DLP is never consulted.
  • Default evaluation is first-match; rule criteria AND together; scan timeout FAILS OPEN (logged as exempted).
  • Caution pages are GET/HEAD-only — they never gate uploads; File Type Control blocks silently produce NO DLP incident and NO auditor email.
  • Rule criteria worth memorizing early: engines AND file types AND users/groups AND locations AND protocols — every leg must match.

Goal: follow one violation through all three after-detection lanes.

200.1 · Advanced classifications — EDM & IDM

Goal: explain the anchor (primary-key) model, the composite (no-primary-key) model, and what actually leaves the customer's premises.

Everything in DS-100 detects data shaped like something. EDM makes the leap to data that IS yours. A pattern dictionary fires on any credit-card number on the internet — including your competitor’s test data and the sample numbers in a vendor PDF. An EDM engine fires only when the value in traffic sits in YOUR indexed table: not "shaped like an account number" but "row 4,812 of our customer database." On exactly the data you care most about, false positives collapse — that is the entire pitch, and it is honest.

The detection model is the anchor: one or two primary fields are the record’s identity (SSN, account number), and secondary fields corroborate (name, DOB, address). Secondaries alone never fire — deliberately, because last names and birthdays appear everywhere; without an anchor they are pure noise. So a match means "the identity appeared, corroborated by its own record’s fields." When no single column identifies a record, the alternative is no-primary-keys (composite) mode: a mandatory field plus at least N optional fields must co-occur. Respect what that switch costs: it is org-wide, it changes the schema philosophy for everything, and flipping it wipes ALL existing EDM schema. It is a program decision made once, early, in design — not an experiment.

The trust story is architectural: the Index Tool is a VM the customer hosts, and hashing happens there — the docs specify 4 CPUs verbatim "for hash generation performance," which only makes sense because generation is local. Your raw CSVs and documents stay on your VM; the index uploads to Zscaler’s distribution endpoint. (The precise "only hashes leave" transport claim is doc-silent — treat it as a tenant/account-team confirmation, not a slide bullet.) And carry the channel matrix into every design conversation, because it limits promises: Inline ✓ but uploads only · SaaS ✓ · Email ✓ · DSPM ✗ (engines referencing EDM are not synced there) · Endpoint uses the same EDM index with an on-device prefilter but builds its own separate IDM index. Finally, program thinking: EDM is a data pipeline, not a checkbox — the index is only as current as its last feed, so the extract-from-source-of-truth and the monthly schedule (2nd–27th UTC) are operating cadence, and a stale index is stale protection wearing a green status.

Hold these facts

  • Index Tool VM is customer-hosted; hashing happens THERE (verbatim: the 4-CPU spec exists for hash-generation performance).
  • Primary = the record's identity; secondaries corroborate; secondaries alone never fire. No-primary-keys mode is an org-wide switch that wipes ALL existing EDM schema.
  • Channel support: Inline ✓ (uploads only) · SaaS ✓ · Email ✓ · DSPM ✗ · Endpoint = same EDM index + on-device prefilter, but its OWN IDM index.
  • The Index Tool is auto-updated by Zscaler (~1 h unavailable, time not changeable); templates are immutable once built — Submit New Data yes, structure changes no.
  • IDM accuracy is chosen per template inside the dictionary (Low ≥25% · Medium ≥50% · High ≥75%) with an Exclude-100% option.

Field numbers: 64 templates per org (each type) · duplicate primaries 512/template, 2,048 org-wide · IDM 100 MB/file, 100 GB org index · strings <3 chars ignored · blank cells never match · monthly schedules: the 2nd–27th (UTC)

200.2 · Endpoint DLP — the device is the perimeter

Goal: narrate the cache-first scan service, the two enforcement engines, and the offline story.

Endpoint DLP moves the perimeter to the device itself, which is why it covers what no proxy can: the USB stick, the printer, the file copied while the laptop is in airplane mode. That reach comes from a different architecture — interception, inspection, and enforcement all live ON the device — and understanding that locality explains every behavior that surprises inline-trained engineers.

Start with the scan service. When a file is touched, the local ZDP engine checks its classification cache first: a hit returns the stored verdict instantly. A miss triggers a live scan — EDM prefilter, local IDM index, local engines — bounded at 15–120 seconds with a timeout default of ALLOW, and the result becomes one cache entry per file. That one sentence explains both why enforcement feels instant in steady state and why the first touch of a big file is slower. Policy updates arrive on a 15-minute pull; between pulls — and on that Wi-Fi-less plane — the device enforces from what it already holds.

Now the part that genuinely surprises inline thinkers: the evaluation model is different here, and it is not optional. Device Control (peripherals) is first-match at plug-in. But Endpoint DLP rules evaluate ALL rules, always, and the most restrictive action wins (ties execute the LOWER order number). There is no positional shadowing on the endpoint, ever: an Allow exception on one rule does NOT immunize a file if a stricter rule also matches it. Engineers who learned "put the allow above the block" spend their first endpoint week confused — this course teaches the model now so you don’t debug it later. Program habit: deploy the channel in observation order — Activities with Sensitive Data first (rule-free tracking of printer/share/cloud/removable movement) to size real behavior, then monitor-mode rules, then enforcement; and hand users the right-click self-service station (revocable external sharing, Manual Protect, EDM Optimizer) so the help desk isn’t your enforcement backstop.

Hold these facts

  • Local ZDP engine: check the classification cache FIRST; miss → live scan (EDM prefilter / local IDM / local engines) → one cache entry per file.
  • Two engines, two semantics: Device Control is first-match at plug-in; Endpoint DLP rules evaluate ALL rules, most-restrictive wins (tie → lower order executes).
  • Activities with Sensitive Data = rule-free tracking on printer/share/cloud/removable; 15-min policy pull; enforcement works offline.
  • The endpoint IDM index is built by right-click "Index Documents" on a delegated admin’s machine — ≤20 files/op, ≤100 MB/file, ≤1 GB/session; ≤100 MB of fingerprints push to endpoints.
  • Self-service station: Share Files Externally (revocable, never transits Zscaler), Manual Protect, EDM Optimizer — all right-click, all admin-delegated.

Field numbers: 15-min policy pull · at-rest scan caps 30/50/100 MB · real-time timeout 15–120 s, default action ALLOW · OTP exemption 5 min–12 h · macOS printing = monitor-only · EDM ✗ clipboard

200.3 · Email DLP — a round trip where Zscaler only tags

Goal: draw the two-leg smart-host loop and name every way it silently degrades to monitor-only.

Email DLP runs on a role split that you must be able to say in one breath: Zscaler inspects and advises; your mail platform routes and enforces. The message’s journey makes it concrete. LEG 1 out: your Exchange/Gmail redirect rule sends outbound mail to the Zscaler smart host, tagged with a tenant-ID header. Zscaler scans it against the engines and writes its verdict as headers — X-Zscaler-Block 0/1, X-Zscaler-Quarantine, or custom X-name:value pairs. LEG 2 back: the mail RETURNS to your platform through a receive connector (with a loop-prevention except-if), and your own transport rules read those headers and do the enforcing — block, quarantine, encrypt, tag, reroute. The custom-header contract is the quiet superpower: any action your platform can take, DLP can now trigger.

The design consequence is the channel’s first law: Zscaler never drops mail. If no platform rule matches the headers — because it was never built, got mis-scoped, or was disabled during a platform change — everything is tagged and everything is delivered. The channel silently degrades to monitor-only with zero errors anywhere. That makes your customer’s transport rules a change-managed deliverable of the deployment, not an afterthought: the project isn’t done when Zscaler scans; it’s done when the platform enforces.

Two semantics to hold: evaluation is per-recipient, most restrictive per recipient, Block > Quarantine regardless of rule order — one email can be allowed to the external counsel and blocked to the personal Gmail in the same send. And quarantine is Exchange-only and must be explicitly mapped; once mapped, Workflow Automation can release or delete quarantined mail (ManageAsApp role) — one of only two write-backs WA has anywhere (DS-200.6).

Hold these facts

  • LEG 1 out: redirect rule + tenant-ID header → smart host. LEG 2 return: receive connector → loop-prevention → YOUR transport rules enforce the X-Zscaler-* headers.
  • Zscaler never drops mail — no matching platform rule = everything tagged, everything delivered.
  • Quarantine is Exchange-only and must be mapped; WA can release/delete quarantined mail via the ManageAsApp role.
  • The header contract: X-Zscaler-Block 0/1 · X-Zscaler-Quarantine (Exchange, must be mapped) · custom X-name:value pairs → ANY platform action (encrypt, tag, reroute).
  • Evaluation is per-recipient, most restrictive wins, Block > Quarantine regardless of order; one email can be allowed for A and blocked for B.

200.5 · Inline mastery — Evaluate All, exceptions, and the org-wide switches

Goal: choose an evaluation mode deliberately and keep the three "exception" concepts straight.

Inline DLP can run under two philosophies, and the org picks exactly one. By Rule Order (the default) walks the list top-down and stops at the first match — which means "exceptions" are positions: an Allow placed above a Block, marked nowhere, working only while the ordering holds. Evaluate All abolishes position: every rule sees the transaction in the same pass, matched rules contribute their actions, and the most restrictive wins (Block > Confirm > Allow). Exceptions stop being positions and become objects: child rules attached to their parent, evaluated top-down first-match among themselves — and a matching child is the FINAL match, decided in that same single pass: it replaces the parent entirely and its action never re-enters the most-restrictive comparison. No rerun, no second vote. The Evaluate all tab teaches this visually with one upload run through both worlds — study it before the Prove-it.

The program angle is timing: switching modes deletes ALL existing inline DLP rules. That makes the evaluation mode a design-phase decision, made before rules accumulate — discovering in month six that you want Evaluate All is a migration event, not a settings change. And if you are replacing a legacy top-down DLP (DS-300.5), notice the fit: a rebuilt-from-intent ruleset drops naturally into Evaluate All, while a ported legacy ruleset — full of positional exception hacks — is semantically wrong in it.

Finally, keep the three things people call "exceptions" permanently separated, because confusing them is the #1 conversation failure on this topic: (1) Evaluate-All exception child rules — this unit; (2) DLP Advanced Settings exemptions (cloud apps/URLs/categories, ≤256 each) which override rules in BOTH modes; (3) Workflow Automation policy exceptions — time-limited per-user subrules written back from an incident, Inline+Email only. Three objects, three consoles, three lifetimes.

Hold these facts

  • Evaluate All: org-wide, account-team enabled, switching deletes ALL inline rules; Block > Confirm > Allow; exception child rules exist only here, REPLACE the parent, and a matching child is the FINAL match in that same pass (no rerun).
  • Three different "exceptions": evaluate-all child rules · Advanced-Settings exemptions (override rules in BOTH modes) · WA policy exceptions (per-user, time-limited, Inline+Email).
  • DLP Advanced Settings is the org-wide switchboard: exemptions, OCR (inline/SaaS/email), EDM variants, GET inspection.
  • Order is only a tiebreaker among same-action matches — and the order-winner is the rule that "triggers" (its notifications and forwarding fire).
  • Advanced-Settings exemptions (cloud apps / URLs / categories, ≤256 each) override rules in BOTH evaluation modes.

Field numbers: Block > Confirm > Allow · child exceptions: first-match, REPLACE the parent, Evaluate-All mode only · switching modes deletes ALL inline rules

300.1 · DSPM — posture for data at rest in your clouds

Goal: tell the five-stage story (template → discover → schedule → scan → classify) with the trust proofs.

300.2 · SSPM & 3rd-Party App Governance — configuration and OAuth-app risk

Goal: onboard any platform through its fixed path and operate both capabilities (posture assessment, 3rd-party app governance).

SSPM is two capabilities behind one portal: Posture Assessment (is the SaaS platform itself configured safely?) and 3rd-Party App Governance (what OAuth applications have your users consented into the estate?). 300.3 · Cross-channel architecture — what is shared, what is walled

Goal: design detection once and predict exactly where it does and does not propagate.

The second design axis is enforcement models: first-match (inline default, Device Control) versus evaluate-all (endpoint always, email per-recipient, inline optional). 300.5 · Replacing legacy DLP — migrate intent, never rules

Goal: plan an incumbent-DLP replacement as a re-baseline of intent — and explain, with specifics, why a lift-and-shift of the old ruleset fails.

Sooner or later a customer hands you an export of 700 rules from their incumbent DLP and asks for "the same thing in Zscaler." The correct answer is no — said well, with reasons. Reason one: a legacy ruleset is archaeology. Ten years of positional exception hacks (allow-above-block tricks nobody documented), dead rules for systems that no longer exist, duplicated rules from admins who couldn’t find the original, and over-broad patterns written to compensate for the old engine’s weaknesses. Port the export and you import all of that dirt — minus the tribal context that made any of it make sense. Reason two: the methodologies genuinely differ. The old world was flat rules in a top-down list; this portfolio composes dictionaries into engines into channel-gated rules, evaluates evaluate-all on the endpoint and per-recipient on email, and offers Evaluate All inline — a positional legacy ruleset is semantically wrong here even where a translation is syntactically possible. Reason three: thresholds don’t transfer. Match counts, confidence scoring, OCR behavior, archive handling, and proximity semantics all differ between engines — the old tuning baseline is not knowledge, it is noise wearing a badge of experience.

The method that works is a re-baseline of intent. First, the intent inventory: for each legacy rule that matters, record what data it protects, whose data, on which egress, with what outcome — and who owns the requirement today. Expect a large fraction to have no owner and no reason to survive; retiring them IS a deliverable, not a shortcut. Second, rebuild detection data-first: predefined dictionaries before custom, EDM from the actual source of truth (informed by DSPM’s inventory — 300.1), engines named by intent. Third, coexist in monitor: run the new stack in monitor mode alongside the legacy tool’s enforcement, compare what each catches on the SAME traffic, and tune with evidence instead of memory. Fourth, cut over channel by channel — enforce in the new, drop legacy to monitor, then retire — never a big-bang flip. And keep the legacy console read-only for its incident history; you are retiring its rules, not your audit trail. Done this way the migration isn’t a risk to the program — it IS the program’s first full loop: discover, detect, monitor, tune, enforce.

Hold these facts

  • Never port rules: legacy exports carry positional hacks, dead weight, and engine-specific compensations that are wrong under this portfolio’s semantics.
  • Migrate the INTENT inventory: data · owner · egress · outcome per surviving requirement; retire the rest deliberately, with sign-off.
  • Rebuild data-first (predefined → EDM/IDM → custom), pick the inline evaluation mode NOW (switching later deletes all inline rules — DS-200.5), and set engine channel gates before policies accumulate.
  • Coexist in monitor and compare on the same traffic; cut over channel by channel; keep the legacy console read-only for history — import nothing.
  • The only things that transfer from the old deployment: your data inventory, your incident history, and the lessons — never the rules, never the thresholds.

Field numbers: none transfer from the incumbent — that is the point. Budget the monitor-coexistence window in weeks per channel, not days.

AI.1 · Positioning — three parts, two products

Goal: explain in one minute why Public AI Security is three parts — and which two are the data-security portfolio.

Framing is the whole battle on this topic, because the market phrase "AI security" hides a category error. AI.2 · Deployment mechanics — the proxy chain

AI Guard is not an agent and not a browser plugin — it is a second proxy hop, reached by a standard ZIA Forwarding Control rule. The mechanics: a wildcard-FQDN group defines the supported AI destinations; traffic matching it is proxy-chained to forward.zseclipse.net:9443 (Fail Close, so a broken chain blocks AI rather than bypassing policy); the AI Guard CA is installed as the chaining root so hop 2 can inspect; QUIC is blocked so traffic stays in inspectable TLS; and the user’s identity rides the X-Authenticated-User header — user-level policy at hop 2 with no second agent. Every one of those is ordinary ZIA plumbing, which is the deployment story’s strength: if the customer runs ZIA today, the AI hop is a rule, not a rollout.

Hold these facts

AI.3 · Policy controls & tenancy

Two control planes live at hop 2, and they answer different questions. Policy Controls answer "may this user use this model at all?" — evaluated first-match, top-to-bottom, over LLM provider/models, users/groups, and Account Type, with no-criteria-match meaning passthrough. Hold these facts

AI.4 · Detectors — prompts, responses, and the three response sources

Hop 2’s detectors are AI Guard’s own catalog — PII, secrets, code, injection/jailbreak, toxicity, topic controls — configured by severity and threshold (lower = stricter) with Allow/Block/Detect outcomes. AI.5 · Files vs prompts · Part 1 endpoint mechanics · logging

This unit carries the three separations that make or break real deployments. Separation one — files vs prompts: a file uploaded to an AI app is judged at hop 1 by inline Web DLP (AI Guard documents no file detectors); the prompt text is judged at hop 2. EDM limits & matching quirks

  • 64 templates per org · duplicate primaries: 512/template, 2,048 org-wide (overflow errors the template that tips it)

  • Primary: alphabetical ≤24 chars; alphanumeric/numeric ≤24 chars, up to 8 variable lengths
  • “.” is a numeric delimiter — Brazil CPF ddd.ddd.ddd-dd doesn’t match; only the undelimited form does
  • Leading/trailing spaces stripped at submit · strings <3 chars never evaluated · blank cells never match
  • Template name, included fields, primary flags immutable — Submit New Data is allowed, structure changes mean recreate
  • Scheduled updates convert to UTC — schedule monthly runs the 2nd–27th

IDM limits & quirks

  • 64 templates per org · 100 MB max per file · 100 GB org-wide index cap
  • First manual save accepts one file only — edit the template to add the rest
  • Scheduled templates: content changes happen on your document server, not in the tool; Verify must pass before save
  • Match accuracy is set per template inside the dictionary (Low ≥25% / Medium ≥50% / High ≥75%), plus Exclude-100%-match
  • Whole-document matching — it will NOT catch a single quoted sentence the way a phrase dictionary would
  • Template name immutable — recreate to rename

Tenant-profile gotcha: allowing a tenant auto-blocks all others AND stops further policy — except YouTube and AWS, where later policies still evaluate and an explicit block rule is required.

The endpoint channel — the device is the perimeter

Endpoint: discovery, device control, and DLP on the machine

Everything happens on the device: an agent discovers and classifies data at rest, inventories applications and peripherals, then two different policy engines enforce — Device Control at plug-in time, Endpoint DLP at data-movement time — all of it working offline. Verified against the legacy-zia Endpoint DLP tree (44 articles, 2026-08-06).

The email channel — a round trip where Zscaler only tags

Email DLP: out to the smart host, back for YOUR platform to enforce

Outbound mail detours through Zscaler's smart host, which evaluates Email-gated engines per recipient — and then only inserts headers. The message returns to Exchange Online or Gmail, where transport rules you wrote do the actual blocking. No matching transport rule means every tagged message is silently delivered.

Gotchas that define this channel

Silent monitor-only
Zscaler only inserts headers. If Exchange/Gmail has no transport rule matching X-Zscaler-Block: 1 (or the quarantine header), everything is tagged and delivered — the #1 email-channel miss.
Mail loops
The return leg re-enters your outbound flow. Without loop prevention (Exchange Except-if on the Zscaler headers; Gmail source-IP exclusion), inspected mail is re-sent to Zscaler forever.
Per-recipient evaluation
Rules evaluate per recipient, most restrictive wins, and Block always beats Quarantine. Quarantine is an Exchange-only action — on Gmail it does nothing.
Propagation & plumbing
Gmail content-compliance changes take up to 24 h to apply. The tenant-ID header must be stamped or the smart host cannot match your tenant. Auditor email needs BOTH an auditor and a template selected — either missing is silent.
Incident management
Same pipeline as inline web: per-rule ZIR/C2C forwarding → your -metadata/-data buckets → Workflow Automation (Source: Email) — and unlike endpoint, WA policy exceptions ARE available for email.

The SaaS API channel — data already at rest, scanned out of band

SaaS Security API: crawl the tenant, judge with the same engines, remediate in place

No traffic is intercepted. Zscaler onboards your sanctioned SaaS tenants via OAuth, a manually started scan crawls content at rest through each provider's API, the same dictionary→engine machinery renders verdicts, and remediation is applied back inside the tenant — quarantine moves, sharing removed, incidents raised.

Gotchas that define this channel

Nothing scans by itself
Policies do nothing until a Scan Configuration exists, references at least one policy, and is manually started. "Scan Initialized" means prerequisites are still being verified — not scanning.
Tenant health is silent
Status must be Active. Validation Failed or Reauthorization Required (an admin role removed, a license lost) silently stops all scanning until fixed.
Cutoff-date reset
Adding or editing any policy rule while a scan runs resets the active/historical cutoff to the edit date — already-processed content becomes historical.
Scope traps
One provider per rule; sites and site groups are mutually exclusive; trusted users/domains make matches "internal" and suppress incidents. Per-app data windows vary (Webex 15-day cap; historical reach ≤6 years).
Public-cloud malware quirk
Bucket selection is circular: save the rule → create the scan schedule → reopen the rule to pick buckets. A rule saved without buckets scans nothing.
Incident management
Same pipeline: per-rule C2C forwarding → your -metadata/-data buckets → Workflow Automation (Source: SaaS). Policy exceptions are NOT available for SaaS — that lever exists only for Inline and Email.

Deep dive · rule evaluation

Evaluate All Rules — how inline DLP really decides

One org-wide switch changes the meaning of every inline DLP rule you own. The default walks rules in order and stops at the first match — an early Allow can silently shadow a Block below it. Evaluate All runs every rule and enforces the most restrictive action, and it unlocks exception child rules that can carve trusted users out of a parent. Verified against the ZIA docs, 2026-08-07.

For top-down natives — the translation

your instinctby rule order (default)Evaluate All
"I need to exempt someone"add an Allow rule ABOVE the Block — and hope nobody ever reorders the listattach an exception child to the rule itself — named, visible, reorder-proof
"I need the Block to win"place it high enough that nothing above shadows itautomatic — most restrictive always wins; nothing can shadow a matching Block
"What does rule order do?"everything — order IS the logictie-break only, among matched rules with the SAME action: it picks which rule "triggers" (whose incident, auditor email, and forwarding fire)
"Where does top-down still exist?"everywhereONLY inside a rule's exception children — first match among the children of one parent

What makes this hard — the exact semantics

One switch, whole org
The evaluation method applies to ALL inline DLP rules. It lives in Administration › DLP Advanced Settings, is enabled by your Zscaler Account team, and changing it requires deleting every existing inline DLP rule first — this is a migration, not a toggle.
Most restrictive, then order
Block > Confirm > Allow. Rule order matters only when multiple matched rules share the same action — then order decides which rule "triggers," and that rule's incident, auditor email, and ZIR/C2C forwarding are the ones that fire.
Exception rules replace, not soften
Children attach per parent (unlimited), carry their own action, are evaluated first-match — and on a match the exception REPLACES the parent entirely and is the FINAL match: the verdict is decided right there, in the same single pass; the exception’s action never re-enters the most-restrictive comparison (practitioner-verified). An Allow child under a Block parent is a full carve-out for that user set.
Three "exception" concepts, three meanings
(1) Evaluate-All exception child rules (this page) · (2) DLP Advanced Settings Cloud App/URL exemptions — override rules in both modes · (3) Workflow Automation policy exceptions — time-limited per-user subrules created from an incident. Confusing them is the #1 conversation failure on this topic.
Cross-channel contrast
Endpoint DLP has no switch: it is always evaluate-all with most-restrictive-wins and the LOWER order number executing on ties. Inline's default is the opposite — first match, full stop.

Public AI Security · three parts, one conversation

Public AI Security — endpoint controls, the inline gauntlet, then AI Guard

Public AI Security is three technologies working one problem. Part 1 — on the endpoint: thick-client AI agents (ChatGPT, Claude, Perplexity desktop) never enter the proxy chain, so Application Discovery maps them, resource groups collect them, and Clipboard Control + Application File Access Control enforce on the device — the local ZDP engine inspecting with the SAME shared DLP engines. Part 2 — inline: web-destined AI traffic runs the ENTIRE inline stack — Cloud App Control, Threat Protection, Web DLP all "still occur here". Part 3 — AI Guard: a Forwarding Control rule proxy-chains AI-destined traffic to a second in-cloud hop with its own admin portal and its own detectors — a prompt is judged twice (inline first, AI-level second), a file upload once, at the inline hop. Endpoint and inline evidence land in the SAME incident pipeline; AI Guard logging is native and separate. Verified against help.zscaler.com/secure-ai-users, 2026-08-08.

Explaining the two journeys

🅟 A prompt
① ZCC→ZIA (IdP-authenticated) → ② full inline stack — CAC, Threat Protection, Web DLP "still occur here"; inline DLP can fire on the POST body → ③ Forwarding Control proxy-chains matching AI domains to forward.zseclipse.net:9443 (fail close, AI Guard CA trust, X-Authenticated-User identity, QUIC blocked) → ④ AI Guard: Policy Controls first-match (LLM provider/models · users/groups · Account Type), then the matched configuration's prompt detectors each vote Allow/Block/Detect → blocked = custom message in place (delivered via the LLM — may misinterpret), optional conversation delete, Reveal → Allowlist → ⑤ not blocked: AI Guard originates the LLM connection → ⑥ the response passes response detectors → ⑦ back through ZIA to the user.
🅕 A file
Same ①–③ — but the judgment happens at hop 1: inline Web DLP (Inline-channel engines) inspects the upload; Block ends it with the normal EUN, and incidents ride the classic chain (auditor · ZIR/C2C → buckets → Workflow Automation). An allowed file then transits AI Guard as passthrough — the secure-ai-users docs define detectors for prompts and responses only, no file inspection. AI-level control of files = control the app, tenancy, and the prompt around it.
Two detection brains — don't conflate them
Hop 1 uses ZIA DLP engines/dictionaries (Common Resources). Hop 2 uses AI Guard's own detectors (PII, Secrets, Code, Text-regex, Injection/Jailbreak, Topic, IP, Competition…) with severity/threshold/action per detector. Nothing is shared between them.
Two consoles, two log worlds
ZIA logs the forwarding transaction in Web Insights and file incidents flow to WA as usual. AI Guard's prompt/response telemetry lives in its own portal (90-day store toggle, Dashboard/Insights) with native exports (S3, Splunk, CrowdStrike, ADX) — no NSS feed, no WA integration documented.
Tenancy restriction
Register your Anthropic Org IDs / OpenAI Workspace IDs; runtime traffic tagging marks matches Enterprise and everything else Personal, and Account Type becomes a policy-control criterion — e.g., strict detectors on Personal, lighter on Enterprise.

AI Guard subscription · ZIA↔AI Guard linked by Zscaler Support · Experience Center enabled · the AI Guard CA uploaded as a Proxy Chaining root certificate · supported app domains in the Wildcard FQDN group.

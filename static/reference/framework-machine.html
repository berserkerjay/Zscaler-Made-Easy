System of record · how the pieces fit · portability guide

One machine, five moving parts

Everything you've built is a single production line: two sources of truth (Zscaler's docs and the POV Builder database) feed four Claude skills, which assemble into four customer-ready framework apps. Nothing writes upstream — each layer only reads the one above it. This page maps the flow, names every required component, and gives the exact checklist for standing it up on another machine or for another user.

The assembly line

Read top to bottom: truth → skills → assembly → output. Every arrow is a real script or a documented read-path — there are no informal connections.

One direction of trust

The reason this stays maintainable: every arrow is one-way. Nothing ever writes upstream.

  • docs → knowledge skillResearch files are verbatim and slug-validated; the skill interprets, the docs stay untouched.
  • knowledge skill → everythingFrameworks and maps read it; a wrong or missing fact becomes a [VERIFY] tag and a logged gap — never an edit.
  • POV app → snapshot → frameworksThe database is the truth. The snapshot is a dated copy; a bad use case is fixed in the app, then re-synced (proven live with UC-0302).
  • arch-viz template → mapsChrome and grammar are fixed so every map looks and behaves identically; only content differs per product.
  • shell → distThe shell is frozen during fills; content packages change. The byte-identical genai regression proves the shell wasn't quietly touched.

Running it somewhere else

Three capability levels — pick the one the new machine or user actually needs. Each level includes everything above it. Distribution model: two private GitHub repos — a monorepo for the four skills + Framework Builder workspace, and the POV app repo carrying its own committed library export. Clone replaces folder-copies and zips.

Level 1 · Present

Just use the frameworks

For a colleague who presents and red-lines, but doesn't rebuild.

  • The four dist/ HTML files. That's it — they're fully self-contained (map and copilot are embedded inside the portfolio).
  • Chrome or Edge to open them. No server, no internet, no install.
Level 2 · Build

Refresh & build frameworks

For a machine that fills, rebuilds, and creates sibling frameworks.

  • Claude Code (or claude.ai with the skill zips uploaded).
  • The four skill folders — knowledge, pov-library (with its snapshot), arch-viz, framework-builder.
  • The Framework Builder workspace: content packages, source/ baselines, MEMORY.md.
  • Python 3 — every script is standard-library only; zero pip installs.
  • Internet to help.zscaler.com only when re-validating doc claims (fills from existing knowledge work offline).
Level 3 · Full stack

Own the POV truth

For the machine that edits use cases and produces fresh snapshots.

  • Docker Desktop + the POV app repo (clone via GitHub Desktop, then docker-compose up).
  • The in-app library export imported — the repo ships empty on purpose; the app's own library export/import is the data transfer path. Commit the export file alongside the repo so it travels with the code. (pg_dump in backups/ remains the low-level fallback.)
  • App reachable at localhost:3100, then sync.py produces the snapshot Level 2 consumes.

Setup order on a fresh machine

For the full Level-3 stack, using the GitHub model: two repos — a monorepo (four skills + Framework Builder workspace) and the POV app repo with its committed library export. Order matters because each step verifies the one before it.

  1. Export the library from the running POV Builder (on the source machine, before anything else).Use the app's own library export and commit the file into the POV repo. This is the data transfer — without it, a clone is an empty app.
  2. Clone both repos (GitHub Desktop is fine), preserving the expected layout.One monorepo: github.com/gagethecade/platformframework — skills, workspace, docs, and the POV app code under pov-app/. Path references inside are repo-relative.
  3. Install the three prerequisites: Claude Code, Python 3, Docker Desktop.Skills load from their folders; every script is Python standard library only — zero pip installs.
  4. Stand up the POV app and import the library.docker-compose up in the POV repo → open localhost:3100 → run the in-app library import with the committed export file → confirm ~405 use cases render.
  5. Run a fresh sync.python3 sync.py in pov-library → check snapshot/SYNC.md shows today's date and ~405 use cases.
  6. Prove the factory with the regression.python3 build.py ../content/genai → output must be byte-identical to source/genai-framework-baseline-v4.html. If it isn't, something didn't transfer cleanly — stop and diff.
  7. Rebuild the portfolio in embed order.Rebuild copilot → embed-copilot.py → embed-map.py → rebuild portfolio.
  8. Smoke-test in Chrome with real clicks.0/8 channels on load → toggle one → tray shows mapped use cases → Portfolio Architecture tabs actually switch (this exact thing broke silently once) → PDF export paginates.

Known portability traps

Verified against the current state of the disk — fix these before handing the stack to anyone.

  • TWO EDITIONS EXIST (transitional) — the repo copies carry repo-relative paths; the original /Volumes/HDD2/… folders still exist with the old absolute references. Until the originals are retired, the repo is the distribution copy — edits must flow original → repo commit (or cut over to working from the clone).
  • EXPORT FIDELITY (verify once) — the data-transfer plan rests on the in-app library export round-tripping everything: internal fields (competitor matrix, review flags, tags, comments), refCodes, and the outcome taxonomy — not just the 10 customer-facing fields. Verify with one export → import → diff before trusting it as the portability path.
  • THE SECOND VOLUME — the app has two Docker volumes, not one. The library export covers the Postgres data; fable_uploads (files attached through the UI) may not be included. If supporting material is uploaded files rather than links, archive that volume separately.
  • EXPORT BEFORE YOU NEED IT — the committed export is only as current as the last time someone ran it — the same way the old backups/ dumps quietly fell weeks behind the live database. Re-export after meaningful library edits; the DB in the volume is always the truth, the export is the traveler.
  • ZIPS ARE OBSOLETE — the existing skill zips are stale (framework-builder.zip predates the latest shell; pov-library has none). Under the GitHub model, don't rebuild them — the clone is the distribution. Keep zips only for claude.ai skill uploads, generated fresh from the repo when needed.
  • MEMORY DOESN'T FOLLOW THE USER — project MEMORY.md files travel with the repo (good), but Claude's per-machine auto-memory does not. A new user's first session should start by reading the Framework Builder MEMORY.md CURRENT STATE block — that's the designed recovery path.
  • EMBED ORDER — rebuilding the portfolio without re-running the embed scripts ships a stale map/copilot silently. The order is: copilot build → copilot embed → map embed → portfolio build.
  • PRIVATE REPOS ONLY — the pov-library snapshot and the committed library export both contain the full internal record — competitor matrix included. GitHub works, but the repos must be private; the customer-facing/internal boundary is enforced at consumption time, not in storage.

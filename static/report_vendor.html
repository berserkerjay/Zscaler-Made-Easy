Migrate from another DLP

Turn a Symantec, Forcepoint, Netskope or Skyhigh DLP policy export into disabled ZIA dictionaries, engines and rules on every channel (web, endpoint, SaaS Security API, email), through decisions a person reviewed. Each adapter reads its vendor's own export file types and shows the API cross-reference from the vendor's objects and fields to ZIA's. Nothing is inferred from the vendor's file beyond each policy's id, name, status and the detection facets its field names expose; nothing is written to the tenant; every generated rule is DISABLED until change control enables it.

Review the decisions

  1. Click Download decisions template: it carries this export's SHA-256 and lists every policy with nothing approved.
  2. For every policy, either approved target translations, one decision per channel (copy the entry to carry a policy to more than one), or an approved retired / out_of_scope disposition with a reason. Each translation names its channel and the channel's action, one to four engine_refs, a unique order from 1 within that channel, scope_acknowledged_any: true because the generated rule applies to Any user and location, and the channel's own fields (listed under _channels in the template):
    • web (Inline Web DLP): action BLOCK / CONFIRM / ALLOW.
    • endpoint (Endpoint DLP, Client Connector): action ALLOW / BLOCK / CONFIRM and data_transfer_method, one of REMOVABLE_DRIVE_TRANSFER, NETWORK_DRIVE_TRANSFER, APPLICATION_FILE_ACCESS, PRINTING (one per rule); device_trust_levels optional.
    • saas (SaaS Security API): action OFLCASB_DLP_REPORT_INCIDENT / OFLCASB_DLP_ALLOW, saas_type (OFLCASB_DLP_FILE, …), tenants (onboarded tenant names, or "variable"), a target_name of at most 31 characters; the remediation you intend (quarantine, remove sharing) goes in designed_action and is set in the portal once incidents are reviewed.
    • email (Outbound Email DLP): action ALLOW / BLOCK, tenants as for saas; a custom header goes in designed_action CUSTOMHEADERINSERTION with custom_header (the zscaler/zia provider does not accept it as an email rule's action), recorded in the report and set in the portal once incidents are reviewed.
  3. Spell out the dictionaries (phrases, patterns) and engines (a ZIA expression; {{dict:ID}} references a dictionary in the same file) and approve each one.
  4. Facets the mapping cannot compute (predefined identifiers, EDM, IDM, ML) are listed under each policy's attest; set carried to true, false or a fraction with a note once you have built the equivalent by hand, and the efficacy mapping counts it.
  5. Upload the reviewed file below and compile. Anything unmapped blocks the run and is listed as a question; the report ends with the efficacy mapping, the share of each policy's recognised detection the translation carries.

What happens next

Every generated rule, on every channel, is DISABLED and applies to Any user and location. SaaS Security API rules ship as report-incident with the intended remediation recorded, and an email custom header is recorded the same way (the zscaler/zia provider does not accept it as an email rule's action); SaaS and email tenant ids are looked up by name or left to a Terraform variable; an endpoint CONFIRM rule binds the tenant's user-confirmation template through a variable. Hand the Terraform workspace (.zip: the same file layout as the pack hand-off, terraform fmt-clean, with a README, variables, outputs and the migration report) or main.tf.json (the same configuration as one JSON file; use one, not both) to the platform team, run terraform init / validate / plan, apply in a test tenant, compare source and target incidents in monitor mode, then enable the rules one by one and order them with the tenant's existing policy. This page never contacts a tenant.

The framework: how Zscaler processes a policy, device to incident
This view models the relevant web-request controls, starting from a candidate Client Connector app profile and forwarding profile for the network you chose, then Cloud App Control, URL Filtering, SSL Inspection, File Type Control and Web DLP, with separate Endpoint DLP, SaaS Security API and Email DLP inventories. Those channels were not tested on this data. Execution and prerequisites depend on the channel and operation; this reference does not prove that every displayed stage executed.
How it works
  1. Type a destination exactly as a user would: a full URL, a hostname or an IP address. Pick the network the device is on and its platform.
  2. Analyze. The first run reads the tenant (Client Connector profiles, PAC files and every ZIA policy: about a minute of API calls, shown live). Later runs reuse that read and only look the destination up, so they take a few seconds.
  3. Read the verdict. One line says where the traffic ends and which object decides it; below it every point that blocks or impacts the traffic is listed with the rule or profile by name, then the path hop by hop against the framework above.
Nothing is written to the tenant. This is a configuration prediction, not an observed transaction or payload scan. Identity-scoped rules remain conditional; the assumptions are listed under every result.

Or import a HAR file (browser developer tools, Network tab, Save all as HAR) to analyze every host a user's session reached. The file is read in this browser and never uploaded: cookies, headers, URL paths and bodies stay here; only the host names, request counts, methods and upload sizes are sent. Up to 100 MB and 200 hosts per run (hosts that sent data first).

The framework: how Zscaler processes a policy, device to incident
Every analysis below walks this exact order — Zscaler's own documented policy-enforcement sequence — starting from the destination's assigned Client Connector app profile and forwarding profile for the network you chose, then Cloud App Control, URL Filtering, SSL Inspection, File Type Control and Web DLP, with Endpoint DLP, SaaS Security API and Email DLP evaluated in parallel on the same data. Nothing here is specific to one destination; it is the reference every result is measured against.
How it works
  1. Type a destination exactly as a user would: a full URL, a hostname or an IP address. Pick the network the device is on and its platform.
  2. Analyze. The first run reads the tenant (Client Connector profiles, PAC files and every ZIA policy: about a minute of API calls, shown live). Later runs reuse that read and only look the destination up, so they take a few seconds.
  3. Read the verdict. One line says where the traffic ends and which object decides it; below it every point that blocks or impacts the traffic is listed with the rule or profile by name, then the path hop by hop against the framework above.
Nothing is written to the tenant. The answer is the configuration's answer for any user, group and location at this moment, not a transaction log; the assumptions are listed under every result.

          The framework: how Zscaler processes a policy, device to incident
          Every analysis follows this order. With ZPA in scope, ZPA is checked first (application segment, bypass, client forwarding and access policy): a destination ZPA carries never reaches ZIA. Otherwise the path starts from a candidate Client Connector app profile and forwarding profile for the network you chose (for a workload, the Cloud or Branch Connector forwarding rules), then the PAC file, evaluated for the destination but never run, then the ZIA modules: Advanced Threat Protection, Cloud Firewall, DNS Control, Cloud App Control and URL filtering, SSL inspection (which decides what the later modules can see), Sandbox, File Type Control and Web DLP. Traffic that is not web is decided by the Cloud Firewall (and DNS Control for its lookup). Endpoint DLP, SaaS Security API and Email DLP are separate inventories, not tested on this path. This is a configuration prediction: it does not prove that every stage executed for a real transaction.
          How it works
          1. Type a destination exactly as a user would: a full URL, a hostname or an IP address. Say where the traffic comes from: a user device (pick its network and platform) or a workload (give its source IP, tags and, if you know them, its workload group and connector group). Pick a protocol and port to trace traffic that is not web, such as UDP/443 (QUIC) or TCP/22 (SSH).
          2. Analyze. The first run reads the tenant, only what is in scope on the Scope page (ZPA, Client Connector profiles, PAC files, the Cloud and Branch Connector rules and every ZIA policy: about a minute of API calls, shown live). Later runs reuse that read and only look the destination up, so they take a few seconds.
          3. Read the verdict. One line says where the traffic ends and which object decides it; below it every step before ZIA, in order, and every ZIA module, each with its deciding rule and each of its conditions as match, no match or unknown, then everything that blocks or impacts the traffic, by name, and the path hop by hop against the framework above.
          4. Ask what if. Open What-if to evaluate the rules scoped to a user, group, department or location. Without one, the result lists what the policy action also depends on.
          Nothing is written to the tenant. This is a configuration prediction, not an observed transaction or payload scan. Identity-scoped rules remain conditional unless you give the identity; the assumptions are listed under every result.

          ZPA is checked first when ZPA is ticked on the Scope page. For a workload, tick Cloud & Branch Connector: its forwarding rules decide whether the traffic goes to ZIA, ZPA, direct or is dropped.

          Test a list

          Test many destinations at once and see which are blocked, allowed or sent around Zscaler, and, when your list says what you expected, where to fix each miss. Choose a CSV file or paste the list, then click Test the list.

          One destination per line: an IP address, a CIDR block (up to a /16), a range such as 10.0.0.1-10.0.0.50, a host name or a URL. A first line with column names lets you add: port, protocol, source IP, location, country, category, user, group, department, label and expected (block or allow). The Network, Platform and Tenant above apply. Up to 8 MB and 250,000 rows; the file is read in this browser and only its text is sent to this app. Nothing is written to the tenant.
          100 destinations per request; ZIA allows about 400 an hour.

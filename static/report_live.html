What this does and does not cover. This feed shows Workflow Automation's DLP-matched incidents only — the user, the rule and dictionaries that matched, and the destination, live as they land. It does not cover URL Filtering, Cloud App Control or Firewall & DNS Control decisions that never trip a DLP rule; that wider transaction log is Web Insights / Cloud NSS, a feed to your own log store (Splunk, S3, a syslog receiver) that this app does not read. Nothing is written to the tenant.

The DLP chain, live: where this session's incidents went

Content captured on a channel → dictionaries (typed, carry the confidence, report match counts) → the DLP engine (Boolean expression, match counts, the Channels gate; at most four engines per rule) → the channel rule acts → it forwards on its own: the evidence lane to Workflow Automation, the telemetry lane to your SIEM, auditor email and third-party ICAP beside them. Until the first incident lands every lane idles; then each channel that raised one carries bits through its rule and the evidence lane to Workflow Automation, faster the more it raised, with its rule tagged enforce or monitor. Each incident as it lands

Every new incident in this feed flies through its own lanes: the channel that captured it, the dictionaries and engine that matched, the rule, the action that rule is configured with now, and the incident receiver that forwarded it to Workflow Automation. The list under the picture says the same in words, without user or file names.
How it works
  1. Start live feed. The first poll looks back two minutes so it does not dump history; every poll after that only asks for what landed since the last one.
  2. Watch it fill. Every ~15 seconds a new poll runs; new incidents appear at the top of the table with who, the trigger, the destination and whether the matched rule blocked or only logged it.
  3. Stop any time; the tally and the rows stay on screen until you Reset session.
